# Room generation algorithm

> Repo note for GitHub issue #12 — design decision. Top-down tiled, single-floor roguelike shooter, seeded RNG, LÖVE 11.5. **Decision: grid-of-rooms with connecting corridors, with an explicit boss/exit room slot.**

---

## Recommended algorithm

**Grid-of-rooms with connecting corridors (the RogueBasin "Grid Based Dungeon Generator")**, extended with an explicit exit/boss-room slot.

### Why it wins vs the other two, for THIS game

The three needs are: a **compact single floor**, **guaranteed connectivity**, and a **natural home for a single exit/boss room**.

1. **Compact + predictable footprint — grid wins.** The grid divides the map into fixed cells; every room is placed inside a cell, so *"rooms can be placed into the space without the need to check whether each room overlaps another room, or falls outside of the dungeon space."* [RogueBasin — Grid Based Dungeon Generator](https://www.roguebasin.com/index.php/Grid_Based_Dungeon_Generator). For a small single-floor map this means no rejection-sampling loop, no rescaling, and a tight, guaranteed packing — exactly what BSP and cellular automata struggle with (BSP tends toward large multi-leaf maps; CA produces organic blobs that fill unpredictably).
2. **Guaranteed connectivity — grid wins cleanly.** The grid article separates room placement from corridor building: *"the corridor building code is separate from the room building code, [so] many types of dungeons can be created using different corridor building algorithms."* [RogueBasin — Grid Based Dungeon Generator](https://www.roguebasin.com/index.php/Grid_Based_Dungeon_Generator). A "connect this room to the previous room" corridor pass produces a spanning tree — every room is reachable with no backtracking or islands, and it is trivially verified by flood-fill. BSP is also fully connected by design (each leaf connects to its sister recursively), but it gives you *roughly* room-sized partitions that are less controllable on a tight floor; cellular automata **explicitly documents the disconnected-cave problem** as a core disadvantage: *"The problem is that the results are inconsistent. The algorithm prone to generating disconnected maps."* [RogueBasin — Cellular Automata Method](https://www.roguebasin.com/index.php/Cellular_Automata_Method_for_Generating_Random_Cave-Like_Levels).
3. **Natural boss/exit slot — grid wins.** Because rooms are discrete slots in a grid, one cell is trivially reserved/dedicated as the exit room. The grid article even shows cells are "marked as used" as rooms are placed [RogueBasin — Grid Based Dungeon Generator](https://www.roguebasin.com/index.php/Grid_Based_Dungeon_Generator), so you can pre-slot a boss cell (e.g. the farthest cell from spawn) before filling the rest. In CA there is no discrete room bound to hang a boss room on; in BSP the exit room is a leaf like any other and the "deepest/farthest" choice is less legible.

BSP is the stronger second choice (good connectivity, nice multi-branch feel), but overkill and looser on a *compact single floor*. Cellular automata is the wrong shape entirely for a discrete, corridor-linked shooter floor.

## Why not the other two (explicit)

- **BSP tree** — Excellent connectivity (each leaf connects to its sister bottom-up, guaranteeing a connected dungeon: *"we repeat the process until we have connected the first two sub-dungeons A and B"*) [RogueBasin — Basic BSP Dungeon generation](https://www.roguebasin.com/index.php/Basic_BSP_Dungeon_generation). But it partitions *then* carves rooms, giving room sizes that vary with the tree and demanding careful split-position tuning (`0.45–0.55` homogeneous vs `0.1–0.9` heterogeneous [same source]) — more knobs than a tight single floor needs, and a less obvious home for one boss room.
- **Cellular automata** — Organic caves are the *opposite* aesthetic for a tile shooter, and the canonical CA article lists as a disadvantage: *"Generating isolated cave sections, possibly blocking player advancement"* and calls the disconnected maps *"the isolated cave problem."* It also notes *"Very large maps tend to not look as natural, or may require some very fine tuning."* [RogueBasin — Cellular Automata Method](https://www.roguebasin.com/index.php/Cellular_Automata_Method_for_Generating_Random_Cave-Like_Levels). Fixes (fill in all but the biggest segment / carve corridors between segments) add post-processing you don't need when connectivity is already by construction in the grid approach.

## Concrete seeded generation recipe (deterministic given a seed)

All randomness must go through `love.math.random` after `love.math.setRandomSeed(seed)` (see LÖVE gotchas). Steps in order:

1. **Choose the grid.** Pick a cell size (e.g. 5 tiles, room max = 4). Derive cell count from the map: `cellsX = mapW / cellW`, `cellsY = mapH / cellH`. Common sizes for a compact floor: map ~40×30 tiles, cell 5 → 8×6 = 48 candidate cells. [RogueBasin — Grid Based Dungeon Generator](https://www.roguebasin.com/index.php/Grid_Based_Dungeon_Generator)
2. **Seed RNG.** `love.math.setRandomSeed(seed)` *before any* `love.math.random` call. (Seed could be a saved string hashed via `love.data.hash` for a memorable seed input.)
3. **Reserve the boss/exit cell.** Deterministically pick a slot for the exit room — e.g. the cell **farthest** (Chebyshev or Manhattan) from the designated spawn cell; mark it used and give it the boss flag/exit marker. This guarantees the exit is meaningfully deep without extra code.
4. **Generate the room list.** Randomly choose how many rooms (typically 3–8 for a compact floor) and each room's width/height (min 2, max cell_size−1). For each, select a random **unused** cell and draw the room's floor rectangle inside it; mark that cell used. No overlap/bounds checks are needed because cells already bound rooms (*"rooms can be placed into the space without the need to check whether each room overlaps another room, or falls outside of the dungeon space"*). [RogueBasin — Grid Based Dungeon Generator](https://www.roguebasin.com/index.php/Grid_Based_Dungeon_Generator)
5. **Connect rooms (guaranteed connectivity).** Pick the spawn room as root. For each remaining room in the order they were placed, carve a corridor from the **current room to the immediately-previous room** ("connect this room to last room" style). This yields a spanning tree: every room has exactly one path in, so the whole floor is connected by construction. Corridors: if face-to-face, straight L; else a Z/elbow corridor. Door placement is easy because the room list already holds room borders (grid article: *"as the corridor building algorithm reaches a room, it simply checks to see if it has reached the border of the room. If it has, a door can be placed."*) [RogueBasin — Grid Based Dungeon Generator](https://www.roguebasin.com/index.php/Grid_Based_Dungeon_Generator)
6. **Verify connectivity (belt-and-suspenders).** Run a **flood-fill** from the spawn tile over walkable (floor/corridor) tiles. Assert the reached set contains ≥1 walkable tile of every room (including the boss room). Because steps 4–5 are deterministic given the seed, a failed assertion means a generator bug, not randomness — fail loudly in dev.
7. **Place spawn + exit.** Spawn = designated root room; exit/boss = the reserved cell from step 3 (place the exit tile / boss trigger there).

This recipe is fully deterministic: identical seed → identical map, every run, every platform (given `love.math.random`, which is platform-independent — see gotchas).

## LÖVE-relevant gotchas (seeding, reproducibility, verification)

- **`love.math.random` is NOT `math.random`.** For reproducible, seedable generation use `love.math.random`, *not* Lua's `math.random`. The local REFERENCE.md explicitly warns: *"`love.math.random` is not `math.random` — for reproducible tests set the LÖVE seed, not Lua's."* [REFERENCE.md — LÖVE 11.5 gotchas](file:///home/encetroc/love2d_wayfinder_test/.agents/skills/love2d/REFERENCE.md)
- **`love.math.random` is platform-independent, `math.random` is not.** Love wiki: *"Generates a pseudo-random number in a platform independent manner."* [love2d wiki — love.math.random](https://love2d.org/wiki/love.math.random). And the rxi/lume issue notes Lua's `math.random` "can vary by platform," which would break shared-seed reproducibility across machines. [rxi/lume issue #12](https://github.com/rxi/lume/issues/12)
- **`love.math.random` is seeded at startup with time, so you must call `love.math.setRandomSeed(seed)` before generating.** Love seeds it automatically at startup (`Math::Math(): ... rng->setSeed(seed)` where `seed = time(nullptr)`) [love2d/RandomGenerator.cpp + MathModule.cpp](https://github.com/love2d/love/blob/main/src/modules/math/MathModule.cpp), so without an explicit `setRandomSeed` you get a different map each run. Set it once, first, in `love.load` (or before any `love.math.random` call). [love2d wiki — love.math.setRandomSeed](https://love2d.org/wiki/love.math.setRandomSeed)
- **`love.math.noise` (a.k.a. `love.math.randomNoise` / Simplex / Perlin) is NOT seedable and is the wrong tool for a seeded map.** It returns "the same value, given the same arguments" and is **independent of the RNG seed** — the LÖVE forum confirms the built-in noise "doesn't allow me to add a seed." [love2d wiki — love.math.noise](https://love2d.org/wiki/love.math.noise); [LÖVE forum — How to add seed to Perlin noise?](https://love2d.org/forums/viewtopic.php?t=82818). Use it only for ambient texture/noise, not map layout. Also avoid `love.math.noise` for large coordinates (precision/banding above ~200k) [love2d/love issue #1579](https://github.com/love2d/love/issues/1579) — irrelevant here, but a good rule of thumb.
- **11.5-specific**: the reference-cheat-sheet renames (`love.math.perlinNoise`/`simplexNoise`, `love.data.lz4`) are the **12.x** branch; this repo is 11.5, where `love.math.noise`/`love.data.compress` are the correct forms. [REFERENCE.md](file:///home/encetroc/love2d_wayfinder_test/.agents/skills/love2d/REFERENCE.md)
- **Verification of layout/connectivity.** Performance is trivial at this size — build the map as a 2D array in `love.load`, run a flood-fill `assert` (step 6) immediately after generation, and only then cache the tile grid for rendering (render from state; create assets once — build `ImageData`/quads in `love.load`, not per-frame) so nothing is rebuilt and the GC isn't flooded. [REFERENCE.md — LÖVE 11.5 gotchas](file:///home/encetroc/love2d_wayfinder_test/.agents/skills/love2d/REFERENCE.md)
